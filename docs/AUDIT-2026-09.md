# WheelDeal - the full-spectrum adversarial fleet audit

## What was asked, and what was done

The owner asked for a full-spectrum adversarial audit of the whole repository
by a fleet of 60+ subagents; no unverified assumption to be implemented; a
strict three-agent refutation review (correctness, latency, rules) on every
candidate fix BEFORE code moved; every verified bug fixed; the full test
suite, typechecks and build scripts run to a clean green; and a report of the
root causes discovered and refuted, every commit and file, and the
infrastructure-level requirements no code can close.

The fleet ran in seven phases. Nothing below is a plan: every number is
reconciled against the workflow journals and `git log`.

| Phase | What ran | Agents that completed |
|---|---|---|
| 1 Discovery | ten repository mappers, one lens each | 10 |
| 2 Audit | 55 distinct adversarial lenses, units A-E | 56 |
| 3 Refute the FINDINGS | correctness lens, batched, default-refuted | 45 |
| 4 Repair | one agent per batch, in its own git worktree, on its own branch | 35 |
| 5 Refute the FIXES | regression / latency / rules, per group diff, per finding | 61 |
| 6 Apply, gate, merge | main loop, serial, one group at a time | 0 |
| 7 Report | main loop's ledger + the journals | 0 |

(Phase 2 shows 56 for 55 lenses because one lens was replayed when a lane was
resumed. The counts are agent transcripts that finished with a result; another
214 attempts were killed by quota trips and resumed from cache. See "How the
repair actually ran" below.)

**The counts.** 292 raw findings deduplicated to **265** (F001-F265), plus
**61** candidates the ten mappers raised on the way (M1-M61), plus the **16**
defects the repo's own docs already admitted were open (A1-A16) - **342 items
in total**, every one of which got a verdict from an adversarial refuter that
was told to default to REFUTED and to cite the code it had read.

| Verdict | P0 | P1 | P2 | total |
|---|---|---|---|---|
| Survived refutation | 4 | 124 | 159 | **287** |
| Refuted | 0 | 2 | 53 | **55** |

Severity was assigned by the finding agent and could only be CONFIRMED or
LOWERED by the refuter, never raised, so no unit could inflate a P2 into a P1
to get it fixed.

Per the owner's two standing decisions, **P0 and P1 were repaired and P2 was
reported, not applied**, and each repair group was merged to `master` on its
own, with CI confirmed green before the next group started.

## Root causes, as patterns

287 verified items is a list nobody reads twice. They are not 287 unrelated
mistakes: they fall into nine families, and each family has one rule that
prevents the whole family. The families are what this audit is actually
worth.

### 1. The write that reports a success it never had

By far the largest family, and the one the repo's own golden rules already
name. Supabase writes come back as bare booleans; dozens of call sites
discarded them, or returned `ok: true` beside them, or read back the value
from the same in-memory pin the failed write had just seeded.

The consequences were not cosmetic. A shop's "stop" that failed to persist
left the permanent opt-out veto with nothing to read on the next instance
(F013, P0). A delivered send whose outbound row was lost killed the shop's
whole conversation as an unknown thread (F014). Mass outreach reported
"queued" with an ETA for a park row it never checked (F015, F038). The
traveller's takeover switch, their accept of a substitute vehicle, and their
booking taps all painted a refused write as the new state (F017, F016, F054).
Admin saves for the tester allowlist, bookings, the wa queue, feedback and
training all answered ok over writes that had not landed (F197, M45).

**The rule now:** every write on a user-visible path reports whether it
PERSISTED - a read-back that cannot be served by the failed write's own cache,
and a 502 when the durable write did not land.

### 2. One fact, two spellings, two keys

A shop's phone number reaches this app in two spellings: the national form
Google Places returns, and the international JID WhatsApp sends. Anything
keyed on the raw string is therefore two things.

The cancel tombstone was read by exact `to_number` while its own unique key
and its clear path were spelling-tolerant, so a shop stored under the other
spelling was auto-messaged after the traveller had removed it (F035, P0). The
8s per-recipient mutex took two different slots for one shop, so both messages
went (F036). Human takeover was stored under one spelling and matched under
the other, making the in-app switch invisible to the send guard (F176). The
funnel ledger and the engine built the thread key two different ways, so one
shop could hold two rows in a primary-keyed table, one with the stage and one
with the state (F133). And the erasure and DSAR prefix filter built a
PostgREST `like.` pattern from the raw email, so an address containing `_` or
`%` matched ANOTHER account's rows - exported by DSAR and deleted by erase
(F022, P0).

**The rule now:** one canonical key builder (`canonicalThreadKey`,
`numberFilter`, `outboxKey`, `phoneKey` in `src/lib/wa/phone-key.ts`), used by
every reader and every writer, and every value interpolated into a PostgREST
filter is escaped for that filter's grammar.

### 3. An abort read as an answer

`fetch` failures and timeouts arrive as `{ ok: false, status: 0 }`. Treating
that as "the server said no" or "the list is empty" turns a transient network
event into a permanent wrong conclusion, and often into an unbounded retry.

The missed-reply recovery read treated a status-0 abort as "this body shape is
empty" and paid three 12s retries inside the webhook (F044). The media ladder
retried the same abort three times, 43 seconds, inside a 90s request (F047).
The connection probe registered a fresh Evolution instance before checking
whether the user still had a session row, so a surviving outbox row could
re-register an unlinked account (F052). Disconnect and erase both reported a
clean sever over a logout that had never been confirmed (F046, F050, F057).

**The rule now:** an ambiguous transport result is its own class - never
"empty", never "refused" - and it is surfaced honestly (a 502, a breadcrumb, a
retry that is bounded and visible) rather than absorbed.

### 4. A budget that is not a wall

Every hot path in this app has a stated budget. Several of them were advisory:
they were checked once at the top of a loop and then not enforced, or they
started their clock after the unbounded work had already happened.

The 90s webhook wall counted the gate and the turn but not the media ladder
upstream of both (F062). The connection probe's 6s budget started AFTER four
unbounded 12s calls (F045). The recovery sweep checked an 8s budget per thread
while each thread ran a 72s turn (F063). The tick's in-call budget was not a
wall, so a fresh 40s drain could start at t=44.9s (F064). Two of the busiest
polls raced the drain against 3s but never passed it a budget, so the drain
ran on detached to its own end (F250). The Meta webhook's drain was unscoped
and unbudgeted (F254). SMTP had no timeouts, so a Gmail stall outlived the
Cloud Run kill and the fallback ladder could never be reached (F042). The AI
and transcription wrappers cleared their abort timer at the HEADER boundary,
so a slow body streamed past the budget (M20) - and the same mistake was made
again inside this audit, by the fix for the PayPal timeouts (M21b).

**The rule now:** a budget is passed down and enforced at every level that can
block, the abort covers the body and not just the headers, and the deadline
for one request is threaded through the whole request.

### 5. Parsing that quietly assumes English and Latin conventions

The negotiation reads what shops actually type, which is rarely English and
rarely formatted the way an English price is.

"350rb" read as 350 Indonesian rupiah instead of 350,000, and "2jt" as no
price at all (F100). A price board with `rb`/`jt` suffixes read a thousand
times too cheap - and because a two-row ladder short-circuits every other
reader, that number became the price of record (F101). A weekly or monthly
rate written in any non-English wording was computed and then discarded
(F102). A bare day range, "4-7 days", was read as a rate and minted a phantom
one-per-day offer that beat the shop's own price (F099). Opening hours,
"9.30 - 5.30", parsed as a 27-day rental span, which blanked the digits out of
the message and divided the shop's total by 27 (F103). A span crossing a month
boundary was scored a month short (F105).

**The rule now:** magnitude suffixes are applied BEFORE the plausibility band,
a rate must have more money than units, and a date range must have two
plausible months.

### 6. A denominator nobody checked

Every admin rollup in this app is a decision aid. Several of them were
confidently wrong, which is worse than blank.

Send counters filtered on a `raw.auto` stamp that three of the four outbound
writers never wrote (F085). The escalation KPI collapsed every human takeover
into one bucket because the writer set no `vendor_id` (F089). The leverage KPI
was fed a projection that had dropped the rival fields it measures, so it was
permanently zero (F087). Failover and dropped-send counters shared a 60-row
budget with the turn stream and read zero under load - exactly when they
mattered (F086). The Command Center's alerts read the 30 newest events of ANY
kind, so the once-a-minute cron ping starved the ban-risk alert out of the
window entirely (F078). The health panel's queue depth rendered a confident
zero over a dead store, sitting beside guard counters that correctly went null
(F090).

**The rule now:** a rollup reads what the writers actually stamp (proved by an
executed test over both), and an unreadable store renders as unknown, never as
zero.

### 7. Privacy registered by convention rather than by code

The erasure registry is the single source of truth for what an account owns.
Several tables were excused from it by a comment rather than by a fact.

`agent_golden_cases` was excused as "de-identified at capture" while the
capture stored the traveller's email verbatim in the thread key, with their
request beside it (F169). `wa_processed` and `wa_inbound_seen` were excused as
"no user data" while holding the email in their primary key (F019).
`agent_training` was excused as "owner-authored" while carrying verbatim
cross-user transcripts (F171). Shop photos, voice notes and video audited into
Storage were outside the registry entirely - never erased, never exported,
never pruned (F168). The 180-day de-identify stripped the only two keys the
registry could find those message rows by, so priced transcripts survived
account erasure forever (F025). And the DSAR export's `unreadable` list could
never populate, because the helper it used swallows every failure into an
empty array (F166).

**The rule now:** the registry is proved by execution, an excuse names the
mechanism that makes it true, and an export says what it could not read.

### 8. Authorization by route rather than by data

The repo's rule is that transcripts are owner-only. Several routes enforced
that on the surface that displays them and not on the surface that serves
them: the training tab, the wa-queue previews and the Data tab all served the
same cross-user text to any management admin (F162, F163, F172). The five
owner-only transport switches were writable by any admin through the
management-gated Key Vault POST, because the gate was on the route and not on
the key being written (F164).

**The rule now:** the gate follows the DATA. A route that can return
transcript text is owner-only regardless of which tab reaches it, and a
config write is gated per key.

### 9. Docs that drifted from the code, on paths that cost money

Documentation drift is usually a P2. Two instances here were not. The
copy-paste Oracle host command in `GUIDE.md` set the Evolution save-data
posture INVERTED, so any host built from it serves an empty message store and
the missed-reply rescue silently recovers nothing for that host's travellers
(F221) - and the single guard that was supposed to catch it was satisfied by a
correct copy of the block eighty lines above. `WEBHOOK_TOKEN_SALT` was
documented in three places as the rotation knob while both schedulers derived
the token without it, so using it as documented locked the fleet out of its own
heartbeat (F179, M10).

**The rule now:** a doc claim about a mechanism is pinned by a test that
EXECUTES the mechanism, and a guard that reads a config value reads every copy
of it, in every dialect, and asserts the absence of the unguarded shape.

## The four P0s

Four items were graded P0 by their finder AND confirmed at P0 by an
adversarial refuter that was told to default to refuted. All four shipped
first, in one commit, before any other repair work.

### F258 - an anonymous caller could claim a password-less owner account
`src/app/api/auth/login/route.ts:182`

The login route carried a bootstrap branch: when the OWNER account had no
password set, a hardcoded literal was accepted and INSTALLED as that account's
password. The branch was reachable by any anonymous caller, before the owner
had ever signed in. Anyone who had ever seen that literal - it had appeared in
working documents - could take the owner account on a fresh database.

**Fixed by** removing the literal entirely. A password-less account can only be
claimed through the email-verified reset flow or Google sign-in. A fresh
database can be bootstrapped by setting `OWNER_BOOTSTRAP_PASSWORD` (env-only,
8 characters minimum, forced change at first login, 503 when unset). Executed
test: an anonymous POST with the old literal returns 401 and writes nothing.

**What this means for the live app:** nothing changes. Production already has
the owner row with a password set. Only a password-less owner row is affected,
and then only to require Google sign-in or one use of Forgot password.

### F022 - the erasure and DSAR filter could reach another account's rows
`src/lib/privacy/user-tables.ts:180`

Tables whose key is a composite prefix (`<email>:<something>`) were matched
with a PostgREST `like.<email>:*` filter built from the raw address. `_` and
`%` are LIKE metacharacters. An address containing either matched a DIFFERENT
account's rows - which the DSAR export then handed to the requester, and which
erase then deleted. Executed against the live module: `a_b@x.com` matches
`axb@x.com:*`.

**Fixed by** escaping `_`, `%` and `\` before the filter, through one
`escapeLike` helper used by every prefix match. Executed test over the live
module with two adversarial addresses asserts the filter matches only its own
prefix.

### F013 - a shop's "stop" could fail to persist, silently
`src/lib/wa-guard.ts:667`

When a shop replies STOP, the guard records a permanent veto. The stamp
discarded the boolean its write returned, so a write that failed left the veto
existing only in a process-local Set - honoured for the rest of that instance's
life and invisible to every other instance and every later cold start. The
next drain on another instance would message a shop that had asked not to be.

**Fixed by** making the stamp report persisted-or-not, retrying the narrow
column rung, and writing the marker row the guard already reads as a fallback
when the durable write fails. Executed test with a store that refuses the
write asserts the next `guardOutbound` still refuses to send.

### F035 - a cancelled shop could still be messaged
`src/lib/wa/cancellations.ts:135`

When a traveller removes a shop, a tombstone is written. The tombstone was
READ by exact `to_number`, while the clear path and the outbox key were both
spelling-tolerant. A shop stored under its other spelling - which happens
whenever the number came from Google Places rather than an inbound message -
was still auto-messaged after the traveller had removed it.

**Fixed by** reading the tombstone through the same `numberFilter` the clear
path uses. Executed test: a tombstone written under spelling A refuses a send
attempted under spelling B. F036 (the 8s recipient mutex) and F176 (human
takeover) share the root cause and shipped in the same commit.

## What the fix panels caught

The owner's instruction was explicit: *"Do NOT implement unverified
assumptions. Run a strict 3-agent refutation review (correctness, latency,
rules) on every candidate fix before modifying code."* Every group's diff went
to three refuters, each with a distinct lens and each told to refute any id it
could not positively clear:

- **regression** - its own detached worktree at the group's head; the three
  typechecks; the FULL vitest suite; then the red check, which restores every
  non-test file in the diff to the base commit and requires each new test to
  FAIL. A test that stays green without its fix proves nothing and is a
  refutation.
- **latency** - does any hunk add a round trip, a synchronous read, an awaited
  write or an unbounded wait to `spte/live.ts`, `processVendorReply`, the
  Evolution webhook, the guard, the drain, the three cron routes, or mass
  outreach?
- **rules** - the DO-NOT-TOUCH anti-ban constants, the hyphen ban, catalogue
  regeneration, the events and erasure registries, `source-bytes`, secrets,
  model identifiers, and the doctrine that a test must EXECUTE its subject.

**Seven fixes were sent back before they shipped.** This is the part of the
audit that cannot be reconstructed from the diff, so it is recorded here in
full.

## How the repair actually ran, and what it cost

**One agent per batch, in its own git worktree, on its own branch.** Each
repair agent got its group's full finding records - the finder's evidence, the
failure scenario, the proposed fix, and the correctness refuter's `fixConcern`
written specifically to warn it - and had to, per finding: write the executed
test FIRST, prove it FAILS on the unfixed tree, implement the smallest correct
fix, prove the test passes, then run the three typechecks and every test file
in the touched directories. A repair whose test never failed was rejected in
code before it could reach the panel.

Working on a branch rather than returning a diff was deliberate: a branch
survives an agent being killed mid-run, and this fleet was killed a lot.

**Merging was serial and gated, one group at a time**, exactly as the owner
decided: squash the group's branch onto the development branch, resolve any
conflict by hand, run the full local gate (three typechecks plus the whole
suite, plus `npm run build` and `check:mobile` when a layout file moved),
commit, push, merge `--no-ff` into `master`, push, refresh the Render mirror,
run `deploy-branch-truth`, and WAIT for that group's master CI run to report
success before the next group started. Fifteen groups, fifteen green runs.

By role: 10 repository mappers, 56 audit-lens agents (55 distinct lenses, one

## What no code can close - owner actions

These are the things the audit found that a commit cannot fix. Ordered by
what breaks if they are skipped.

**1. Run all three SQL files against the live Supabase project.**
`supabase/schema.sql`, `supabase/perf-indexes.sql`, `supabase/retention.sql`,
in that order. All three are idempotent. Two audit outcomes are inert until
this is done: the index additions the P2 index cluster (F001-F005) asks for
live only in `perf-indexes.sql`, and `retention.sql` is what revokes the anon
grant on `prune_old_rows`. There is now a third reason: G2's erase fix deletes
the `app_users` row only when NOTHING in the walk failed, and on a project
without the `vector` extension the `corpus_embeddings` read 404s and counts as
a failure - so on such a project an erase leaves the account row behind and
answers honestly instead of claiming a clean sever.

**2. If you ever set `WEBHOOK_TOKEN_SALT`, set it as a GitHub repository
secret, not only in the Cloud Run console.** G14 made both schedulers and the
deploy step derive the ping token WITH the salt, exactly as the app does, and
carried the salt into the `--set-env-vars` list. But `--set-env-vars` replaces
the whole service environment, so a salt typed only into the Cloud Run console
is wiped by the next deploy. Set it once in GitHub -> Settings -> Secrets and
it reaches both the service and the two schedulers together. Unset is safe and
is the default: the derivation then produces exactly the historical token.

**3. After any salt change, re-paste `WD_PING_TOKEN` in Render.** That cron's
token is hand-pasted (`sync: false`), so nothing can update it automatically.
Copy the current value from Admin -> Keys. Until you do, that one cron 403s
while the GCP schedulers keep working.

**4. Rebuild or fix any Evolution host built from the old GUIDE.md one-liner.**
F221: the copy-paste Oracle cloud-config shipped
`DATABASE_SAVE_DATA_NEW_MESSAGE="false"` and `DATABASE_SAVE_DATA_CHATS="false"`,
the inverse of the posture the missed-reply recovery sweep depends on. A host
built that way serves an empty `/chat/findMessages`, so for every traveller
placed on it, a shop reply whose webhook delivery was lost is gone for good.
The file is fixed; hosts already built from it are not. The corrected one-liner
also carries the mandatory 7-day prune sidecar, because turning the store on is
what makes the prune mandatory.

**5. Create the `wa-media` Storage bucket and confirm it is PRIVATE.** No SQL
can set a bucket's visibility. G2 made shop media erasable and exportable
through the registry; the bucket being public would defeat that from outside
the app entirely.

**6. Set `OPERATOR_NAME`.** The Terms and the Privacy Policy name the legal
entity from it, and the admin surface renders red until it is set.

## Two residuals stated plainly, because they are not fixed

- **Rows de-identified by the OLD retention statement stay unreachable.** The
  new statement keeps an erasable key, but nothing can retroactively restore
  one to a row that was already stripped. An erase cannot reach those rows;
  retention will still delete them on schedule.
- **On a lost version race, the thread merge takes the winner's price even
  when the winner has none**, so a losing turn's brand-new price is dropped
  rather than carried. That is the pre-existing "never overwrite a live price"
  policy, not a defect introduced here, and the next turn re-derives it. It is
  written down because it was noticed while fixing something else, and an
  unrecorded observation is how a defect gets rediscovered in six months.
